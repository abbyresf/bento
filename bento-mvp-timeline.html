Phase 1
Backend Foundation
May 1 – May 31

Replace localStorage with a real backend. Nothing else ships until this is solid.

Infra
Choose and provision backend stack Recommended: Supabase (Postgres + auth + real-time, generous free tier, fastest path to MVP). Alternative: Firebase if you prefer NoSQL.
Auth
Implement user authentication Email/password + Google OAuth via Supabase Auth. Replace the current no-account model.
Data
Design and migrate database schema Tables: users, profiles (TDEE/goals/restrictions), meal_history, streaks, favorites. Mirror the current localStorage data model.
Backend
Replace all localStorage reads/writes with API calls Swap out storage.js utilities for Supabase client calls. Keep the same interface so the rest of the app breaks minimally.
Frontend
Build login / signup screens Integrate into existing onboarding flow. New users sign up → onboard → saved to DB. Returning users log in → skip onboarding.
Phase 2
Core New Features
June 1 – June 30

Ship the features that differentiate Bento: streaks, multi-university support, and deeper personalization.

Backend
Streak tracking system Track daily goal-meeting events server-side. Logic: if user confirms all meals and hits ≥80% of calorie/macro target, streak increments. Miss a day → reset. Store current streak + longest streak.
Frontend
Streak UI Streak counter on the meal plan header. Flame icon, current count, milestone celebrations at 7 / 30 / 100 days.
Backend
Abstract university / dining system Move Brandeis-specific config (Nutrislice subdomain, location slugs, meal times) into a universities table. Each university row defines its dining provider, API config, and supported locations.
Data
Onboard 2–3 additional universities Priority targets: other Nutrislice-powered schools (easiest adapter reuse). Add a university selector to onboarding.
Product
Deepen personalization with server-side history With real meal history in DB, the optimizer can weight variety over a rolling 14-day window instead of the current session-only approach.
Phase 3
Weekly Insights + Polish
July 1 – July 24

Make Bento feel smart and sticky. Insights give users a reason to come back every week.

Backend
Weekly insights engine Scheduled job (cron or Supabase Edge Function) runs every Sunday. Aggregates the week's confirmed meals: average macros vs targets, most-eaten foods, best and worst days, streak progress.
Frontend
Insights tab / screen Weekly summary card, macro trend charts (simple bar charts — no heavy charting library needed), streak history, personalized callout ("You hit your protein goal 6 out of 7 days!").
Product
Email digest (optional but high-value) Weekly insights email via Resend or Supabase + SendGrid. Users opt in during onboarding. Drives re-engagement with minimal engineering effort.
Frontend
UI polish pass Responsive audit across all screens, loading states, empty states, error handling for failed API calls. Bento should feel production-quality, not beta.
Infra
Set up staging environment Separate Supabase project for staging. Deploy frontend to Vercel preview URL. Required before any beta users touch the app.

Key Risks to Watch

Dining API instability The Nutrislice API is unofficial. Menu format changes or downtime will break meal generation. Mitigation: robust fallback to cached data, monitoring alerts.
Multi-university data variance Each school's dining system structures data differently. Budget extra time per university beyond the first — the adapter pattern helps but won't eliminate all edge cases.
Auth complexity Migrating from no-account to accounts is the biggest scope risk. Scope it tightly in Phase 1 — don't add social login until post-launch.
Scope creep Four months is tight. If Phase 1 or 2 slip, drop the email digest before cutting any core features. Streaks and insights are differentiators — protect those.
